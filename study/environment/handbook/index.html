Operating principles

What the environment is supposed to protect

The setup has two jobs at the same time: help ship useful software and make the machinery understandable enough that dependence on AI falls over time.

01

Learning stays visible

Routes, models, migrations, containers and tests should be explained in context: what they are, where they belong and why the project needs them.

02

Architecture stays predictable

Routes, services, database code, models, tests and configuration should have stable homes instead of being reorganized on every generated change.

03

Projects stay isolated

Experiments should have bounded environments so breaking one project does not damage another project or production service.

04

Risky changes stay reviewable

Dependencies, migrations, destructive commands, secrets, broad file changes and deployment actions should be visible before they happen.

05

Recovery stays simple

Git checkpoints, database backups, disposable sandboxes and repeatable deployment steps should make bad changes diagnosable and reversible.

06

Local work stays portable

Open-source defaults, Docker and documented configuration should keep projects movable between local machines, VPSs and hosted services.

Proposed project anatomy

A stable place for each kind of backend code

Exact names can evolve as the stack is finalized. The important part is the separation of responsibilities so routes stay thin, behavior stays testable, schema changes stay explicit and secrets stay outside code.

app/
  main.py              # application entry
  api/                # HTTP routes
    routes/
  services/           # business logic
  models/             # database models
  schemas/            # request/response shapes
  db/                 # database setup
tests/                # automated checks
migrations/           # schema history
.env.example           # config names, no secrets
Dockerfile             # runtime package
docker-compose.yml     # local services
pyproject.toml         # Python project/dependencies
README.md              # how to run it

Routes stay thin

Receive input, call the right deeper logic and return a response. Heavy business behavior should not pile up inside route files.

Services hold behavior

Business rules live in Python functions/classes that can be tested without pretending every action is an HTTP request.

Database changes stay explicit

Schema changes produce inspectable migrations, with backup/recovery procedures before risky production work.

Configuration stays outside code

Real secrets belong in environment variables or approved secret storage. .env.example documents names without credentials.

Tests are part of the project

Completion should mean checks actually ran, not that an AI claimed the code looked correct.

Git records the truth

Readable diffs and known-good commits create a concrete recovery path when a generated change goes wrong.

AI-assisted learning loop

Every change should leave understanding behind

The environment is designed so AI can help across real project work while the underlying stack remains visible. The point is to understand more after the change than before it.

01

Describe the goal

Example: add a project-creation endpoint.

02

Map the change

Show files, concepts, risks and expected behavior first.

03

Explain the stack

Endpoint, schema, service, model and migration are explained in context.

04

Build the change

Work stays inside the expected project structure and scope.

05

Run checks

Tests and validation produce evidence before completion.

06

Review the diff

Git shows exactly what changed and leaves a recovery point.

What AI is doing

Planning · editing · explaining · checking

AI can translate intent into files/steps, write bounded changes, explain why the code exists and run approved checks.

What the stack is doing

FastAPI · PostgreSQL · Docker · Git

FastAPI handles web/API work, Postgres stores durable data, Docker creates repeatable runtime boundaries and Git records exact file changes.

Acceptance standard

The environment is ready when these workflows are concrete

A polished UI does not make a development environment finished. It has to be repeatable, inspectable, recoverable and teachable.

○
A new FastAPI project can be created from the standard template

Folder structure, dependency setup and local commands are documented.

○
Local PostgreSQL can be started, migrated, backed up and restored

The database workflow is understandable without depending on a hosted provider.

○
AI permissions and instruction files are visible

You can inspect and change the rules that control generated work.

○
Tests and release checks have one documented command path

Completion means checks actually ran.

○
Bad code and bad data changes have recovery procedures

Git rollback and database restore are both demonstrated.

○
Staging and production are clearly separate

Secrets, data and deployment actions do not blur across environments.

○
The example project completes the full lifecycle

Local development, API, database, tests, Git, deployment, logs and rollback are all covered.

○
The handbook can gradually get out of the way

The long-term result is independent understanding, not permanent dependence on instructions.
