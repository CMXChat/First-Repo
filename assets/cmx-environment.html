02 / operating principles

What this environment should protect

The environment has two jobs at the same time: help ship useful software and make the work understandable enough that dependence on AI falls over time.

01

Learning stays visible

When a route, model, migration, container or test appears, the environment should explain what it is, where it belongs and why the project needs it.

02

Architecture stays predictable

Routes, services, database code, models, tests and configuration should have stable homes so generated work does not reorganize the project on every request.

03

Projects stay isolated

Experiments should have their own environments and containers. Breaking one project should not damage another project or a production service.

04

Risky changes stay reviewable

Dependency changes, schema migrations, destructive commands, secrets, large file changes and deployment actions should be visible before they happen.

05

Recovery stays simple

Git checkpoints, database backups, disposable sandboxes and repeatable deployment steps should make a bad AI change annoying instead of catastrophic.

06

Local work stays portable

Open-source defaults, Docker and documented configuration should keep projects movable between a laptop, a VPS and hosted services without rebuilding the architecture.

03 / delivery path

One understandable route from idea to production

Every real project should follow the same recognizable path. AI can help at each stage, while permissions and checks get stricter as the work moves closer to production.

1

Local

Write code, learn the stack and run the app on the machine.

2

Sandbox

Run isolated experiments with bounded access and disposable state.

3

Validate

Tests, linting, types and migration checks run before completion.

4

Git

Review the diff, checkpoint the work and keep a clean history.

5

Staging

Use production-like services without touching real production data.

6

Production

Deploy a known revision with explicit secrets and release steps.

7

Observe

Read health, logs and errors after release.

8

Recover

Rollback code or restore data using a documented procedure.

Fast path: local experimentation and tests stay quick.Controlled path: staging, secrets, schema and production carry more friction on purpose.

A stable place for every kind of code

Routes stay thin

Endpoints receive input, call the right service, and return a response. Heavy logic should not collect inside route files.

Services hold behavior

Business rules live in Python functions or classes that can be tested without pretending every action is an HTTP request.

Database changes are explicit

Schema changes should produce migrations that can be inspected, applied, reversed where practical, and backed up before risky production changes.

Configuration stays outside code

Real secrets live in environment variables or an approved secret store. .env.example documents expected settings without containing credentials.

05 / AI authority

Helpful access with hard edges

AI should work inside the project with the permissions needed for the task. Higher-risk actions should stop for review instead of inheriting unlimited authority.

allowed

Routine work

Fast feedback inside the current project.

  • Read approved files and documentation.
  • Create routes, services, schemas and tests.
  • Run allowlisted development commands.
  • Explain errors, concepts and diffs.
  • Prepare Git changes on a branch.
→
review

Approval boundary

Changes with larger blast radius pause first.

  • Add or upgrade dependencies.
  • Change database schema or migrations.
  • Modify architecture across many files.
  • Delete important files, data or containers.
  • Deploy staging or production revisions.
  • Use credentials or provider actions.
→
blocked

Never silently

These boundaries should not disappear for convenience.

  • Hardcode secrets or tokens.
  • Access unrelated projects or the whole machine.
  • Rewrite protected Git history.
  • Bypass tests or production approval.
  • Run arbitrary destructive shell commands.

09 / recovery playbook

Bad changes need boring recovery paths

Recovery should rely on known tools and documented checkpoints. The goal is to make failure diagnosable and reversible without guessing.

code

AI changed too much

  1. Stop new changes and inspect git diff.
  2. Identify the last known-good commit.
  3. Save any useful work on a separate branch if needed.
  4. Restore or revert the bad files using Git.
  5. Re-run tests before continuing.
database

Migration went bad

  1. Stop writes if production data could be affected.
  2. Check the migration revision and database state.
  3. Use the documented downgrade only when it is safe.
  4. Restore the pre-migration backup when rollback cannot safely repair the data.
  5. Fix the migration in development before another production attempt.
runtime

Server will not start

  1. Read the first meaningful error in the logs.
  2. Confirm environment variables and dependency install state.
  3. Check the database and required services.
  4. Run the application locally with the documented development command.
  5. Reduce the problem to one failing component before changing architecture.
deploy

Production release failed

  1. Keep the failed revision identified.
  2. Inspect health checks and deployment logs.
  3. Rollback to the last known-good image or commit.
  4. Confirm the previous version is healthy.
  5. Reproduce the failure in staging before trying again.
