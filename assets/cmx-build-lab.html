delivery_pipeline

How changes should reach production

01

Normal-language request

Describe the desired change. The request becomes a tracked plan with scope, affected files, risk and tests.

02

Feature branch

Create a branch from an approved immutable base commit. Main remains untouched.

03

Reviewable changeset

Write only approved files and show the exact diff before higher-risk actions continue.

04

Isolated checks

Run fixed lint, test, build and security profiles inside a short-lived Docker sandbox.

05

Protected preview

Deploy the reviewed revision to a preview or staging environment using separate data and secrets.

06

Draft pull request

Open a pull request containing the plan, diff, checks, risks and review notes. No automatic merge.

07

Production request

Present the release, staging evidence and rollback revision for explicit human approval.

08

Deploy and observe

Deploy only after approval, then watch health, errors and rollback readiness in Build Lab.

readiness

What must exist before AI can safely act

backend_foundation

Required first

Backend, API and AI contracts documented.
Route registry and page responsibilities documented.
Dockerized Python application on a Linux server.
Cloudflare Access and Tunnel protecting the origin.
Secure sessions, roles, capabilities and record ownership.
Separate development, staging and production configuration.
Structured logs, health checks, backups and rollback.

ai_foundation

Required before autonomy

AI risk tiers, approvals and blocked actions documented.
GitHub branch, sandbox, preview and pull request workflow documented.
Versioned project handbook and approved retrieval scopes.
Typed tool registry and capability-specific MCP policies.
Short-lived sandbox service with no shell or host access.
Usage quotas, cancellation, audit logs and emergency stop.
Human production approval isolated from AI credentials.
