main_purpose

Two AI systems under one control plane

operator_and_developer_ai

Build and manage the platform

Understand the approved project handbook, architecture and route registry.
Read approved GitHub files at a specific revision.
Turn a feature request into a visible implementation plan.
Create feature branches and reviewable changesets.
Run fixed tests and security checks in an isolated Docker sandbox.
Create protected previews, staging deployments and draft pull requests.
Request production deployment after review without approving itself.

user_facing_ai

Help authorized users inside the site

Answer questions using approved page, workspace and documentation context.
Summarize authorized records, files, reports and activity.
Generate drafts, checklists, research plans and reports.
Call typed backend tools that the user is permitted to use.
Propose changes to site data and show the exact effect before approval.
Create approved automations with schedules, quotas, logs and cancellation.
Keep each user and workspace isolated from unrelated context.

development_lifecycle

Plain English to reviewed production

01

Describe the goal

Explain the feature, problem or desired outcome in ordinary language.

Original request recorded
02

Classify intent and risk

The server identifies whether the request is an answer, read, draft, write, external action or blocked request.

Risk tier and required approval
03

Retrieve approved context

The AI searches the handbook, route registry and allowlisted repository files at known revisions.

Cited context only
04

Show a versioned plan

The plan lists affected files, APIs, tools, tests, risks and protected areas.

Nothing executes yet
05

Approve the scoped action

Only the displayed plan version and selected actions receive temporary approval.

Approval expires and is audited
06

Create a feature branch

The branch starts from the approved base commit. Main remains untouched.

Immutable base SHA
07

Write the changeset

The AI updates only approved files and creates a reviewable diff.

Branch-only write
08

Run sandbox checks

Fixed test, lint, build and security profiles run in a temporary restricted container.

No arbitrary shell
09

Open a protected preview

The approved revision is deployed with separate test data and secrets.

Cloudflare-protected preview
10

Create a draft pull request

The pull request includes the plan, changed files, checks, risks and review notes.

No automatic merge
11

Validate staging

The reviewed release runs in the protected staging environment with production credentials unavailable.

Separate environment and data
12

Request production approval

The system presents the release, staging evidence and rollback version. A human approves production.

Rollback prepared

framework_position

FastAPI is preferred, while the architecture stays portable

preferred

Dockerized FastAPI on Linux

FastAPI fits the Python learning objective, typed request models, async services, automatic API documentation, Jinja migration path and Docker deployment plan.

decision_rule

Requirements outrank the framework name

A different Python ASGI framework can be selected during implementation only when it preserves the documented APIs, security boundaries, sandbox workflow, staging process, tests, approvals and deployment controls.

non_negotiable_boundaries

The AI remains useful because it remains controlled

allowed_direction

Controlled capabilities

Approved repository reads and feature branches.
Typed backend tools and capability-specific MCP tools.
Sandboxed checks, protected previews and draft pull requests.
User actions with visible effects and confirmation.
Audit logs, quotas, cancellation and emergency stop.

unavailable

Hard blocks

Unrestricted shell, sudo, Docker socket or host filesystem.
Production secrets, raw environment variables or database credentials in AI context.
Arbitrary Python, JavaScript, commands, URLs, MCP servers or provider methods.
Direct writes to main, automatic merges or AI self-approval.
Direct production deployment or cross-workspace data access.

build_order

Foundation before autonomy

Identity, API contracts, tool permissions, jobs, audit logging, staging and cancellation come before user assistants, MCP writes, AI automation and advanced development actions.
